§ Findings

The break, peeled one layer at a time.

The ci-release.yml "Full Test Suite" (pytest + the example pipeline run) only ever triggered on PRs to main/master. Once develop became the integration branch, every feature and dependabot PR targeted it — where CI never ran. The suite was effectively dark, and had rotted in the dark. The first develop run went red on a commit that touched only the workflow trigger, which proved the breakage was pre-existing, not ours.

Layer 1 — conda.sh not found

install_shapepipe looked for conda.sh only under /opt/conda (a docker convention) or $CONDA_PREFIX, neither of which resolves on GitHub runners. Fixed by asking conda where it lives: conda info --base, with the old paths kept as fallbacks. Verified against a non-standard local prefix the old logic would have missed.

Layer 2 — CI built the wrong environment

The install steps called ./install_shapepipe --develop. But --develop only adds dev pip extras into the production env; the flag that builds the dev conda env (shapepipe-dev, from environment-dev.yml) is --env-dev — which also triggers .[dev] on its own. The downstream test step even did conda activate shapepipe-dev, an env the old flag never created. Both install steps now use --env-dev. The dev env solves cleanly (confirmed locally with a conda env create --dry-run).

Layer 3 — production env is genuinely broken

Surfaced while diagnosing layer 2: environment.yml (production) pins astropy==5.2 (which only has py38–py311 builds) against python=3.12 — unsatisfiable. This breaks real production installs, not just CI. It is out of scope for the CI repair and deserves its own issue.

Layer 4 — and the decision to stop digging

Layers 1–2 fixed, the conda env still wouldn't solve cleanly. That was the signal to step back and ask the real question: why is CI building a conda environment at all? The Docker work had already moved the runtime to a slim-Python + apt + uv-frozen story with no conda. The astromatic binaries that were conda's whole reason for existing (psfex, source-extractor, weightwatcher) ship as Debian packages and were already in the image. CI was the last place still carrying a parallel, rotting conda story. So instead of layer 5, 6, 7 — delete it.

The fix: remove conda, test the container (#733)

  • deploy-image.yml now runs the full pytest suite inside the dev image, alongside the existing smokes. Build/ test split from publish: PRs build + test (even from forks), only pushes to develop/main publish.
  • ci-release.yml deleted — the conda suite is gone.
  • cd.yml builds docs in the dev image (pandoc was vestigial, dropped); doc-tests.yml deleted.
  • install_shapepipe, environment.yml, environment-dev.yml deleted. The production astropy bug is now moot — there's no file to fix.
  • Install docs rewritten for the container + uv workflow.

Why push: [develop], not just pull_request

A pull_request run only re-fires when the PR itself changes — not when the base branch advances under it. So two PRs that each pass against develop independently can break it once both merge, with nothing catching the collision. The push trigger tests the actual post-merge develop HEAD. (Not added to master — nothing reaches it except the already-tested develop→master PR.)
